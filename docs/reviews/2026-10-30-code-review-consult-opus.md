# 程式審查與優化計畫：第二意見

審查者：Opus　日期：2026-10-30

範圍：`src/index.html`（af1a0bc）、`db.d.ts`／`user.d.ts`（0.2.92）、`2026-10-30-code-review.md`。我先獨立讀完程式，再讀那份審查。驗證用的腳本放在 scratchpad，沒有進 repo（`scratchpad/opus/verify.js`、`mock2.js`），只用合成資料。`mock2.js` 是原 mock 的變體，多了三個開關：首次快照延遲、latency compensation（自己的寫入在 promise 完成前就送出快照）、讓指定文件的監聽失敗。

## 一、那份審查漏掉的問題

**N1（高，已驗證）資料還沒載入就能寫入，而且會寫錯劑量。** 位置：492 `ready=false`、540–585、954–961、501、494、679。`db` 一連上就可以按按鈕，但 `days` 和 `profile` 的第一筆快照可能還沒到。這段時間畫面顯示兩格「55.0 kg」、服藥是待辦，按鈕也都能按。我把首次快照延遲設成 1.5 秒，並預先放一筆當天早上 52.3 kg 的紀錄，再點服藥。結果文件被 `set` 整份取代，早上體重不見了；服藥紀錄的 `dose` 寫成程式內建的 50，不是設定裡的 75。B1 的修法可以救回被覆蓋的體重，劑量寫錯它救不了。在兩台刀之間「打開就點」正好會落在這段時間。修法：`days` 與 `profile` 都收到第一筆快照之前，寫入控制項一律停用，格子顯示「—」。

**N2（中，已驗證）設定會被整份覆蓋。** 位置：914–915、929、961。`saveProfile` 用本機的 `profile` 做 `set`。`profile` 的監聽錯誤被 `()=>{}` 吞掉，失敗時 `profile` 會一直是 `{}`。我讓這個監聽失敗，再按匯出，結果 `settings/profile` 只剩 `{lastExport, updatedAt}`，藥名、劑量、服用方式都沒了。之後每次服藥都會靜默記成 50 mcg。修法：改用和 `writeDay` 同一套「先 update」的寫入工具，監聽失敗時要在畫面上顯示。

**N3（低，已驗證）過去日期的週點和大標不一致。** 位置：546 對照 526–527。圓點只看早上體重和服藥，`needed()` 對過去日期另外要求晚上體重。所以週點是實心，點進去卻顯示「這天還差 1 項」。

**N4（低）基準截圖測不到 B2。** `baseline.js` 產生的 `wrapped.html` 自己加了 `[hidden]{display:none!important}` 和 `body{margin:0}`。第二節「截圖中沒有問題」只在 claude.ai 外框也有這兩條時才成立。第 0 批的 e2e 不應該注入這兩條，至少要多跑一組不注入的版本。

**N5（低）跨過 18:00 或 04:00 時畫面不會自己更新。** 位置：526、669、949。只有 `visibilitychange` 會觸發重算。頁面一直亮著跨過 18 點，「晚上體重」不會變成待辦。03:50 打開、04:05 才存，會以「補登」寫進前一天。加一個每分鐘檢查一次的計時器就能解決。

**N6（低）對比不足不只一處。** M6 的實際值是 3.7:1，不是 3.3:1。瑜珈膠囊 `#2f8f83` 只有 3.9:1，也低於 4.5:1。週點星期字 `--faint` 在底色上只有 2.3:1，比字太小更嚴重。

**N7（設計，待決定）首屏的升降數字。** 位置：555、586–591。完成後的事實列寫「比前一週少 0.3 kg」，這是升降比較，出現在首屏。CLAUDE.md 寫「首屏不顯示升降評分」，又允許「一行中性事實」，兩句有張力。這要請使用者決定，不是 bug。

## 二、我不同意或認為證據不足的地方

**B1：結論與嚴重度正確，重現方式有偏差。** 原 mock 在 `set()` 完成後才用 `setTimeout` 送出快照。但 `db.d.ts` 寫明「Your own writes appear immediately (hasPendingWrites: true)」。我在 mock 打開 latency compensation 後重跑「服藥→月經」，兩個欄位都有存，重現不了。所以在真實環境裡，同一台裝置連點未必會出事。真正會觸發的是三種情況：N1 的載入前空窗、另一台裝置先建立了當天文件、文件已被刪除。修法照原計畫即可。不過 mock 要加 latency compensation 開關，B1 的測試改用上面三種情境。否則測試通過或失敗的理由，都是 mock 的特性，不是程式的行為。

**B2：問題是真的（我驗證過，不加那條規則時，四個子頁、toast、鍵盤列、匯入按鈕的 `display` 都是 `flex`），但「有條件的高」可以直接判定。** 用手機打開線上網址看一眼，十秒就知道外框有沒有補這條規則。使用者已經在用，大概是有補。一行修正照做，嚴重度依實際看到的結果定。

**B3：嚴重度偏高，修法偏重。** 單人使用時，快照只在資料變動時才來。打字輸入備註的當下，幾乎只有自己的寫入會觸發重繪。我會標低到中。不需要通用的 `setHTML` 加延後機制：`renderToday` 在焦點位於 `#exToday` 內時跳過重建這一塊即可。設定表單只在進入頁面時填值，之後用一個 `dirty` 旗標擋住快照覆蓋。兩處加起來大約十行。

**B6：證據不足，理由有誤。** 661 行只有在 `v!==curVal()` 時才把狀態設成 touched，吸附回同一個刻度不會觸發，所以「沒碰尺，灰色狀態就消失」不成立。「宣告了 `programmatic` 看得出原本想修」是推測。±0.1 改成立即捲動、程式捲動期間忽略 scroll 事件，這兩項便宜又安全，可以做。但「touched 只由觸控／指標事件判定」等於改寫輸入模型：iOS 的慣性捲動在手指離開後還會繼續，鍵盤方向鍵也要另外處理。應該等手機實測確定有問題再做。

**B5：** 同意。內建的服藥劑量 50（494）是同一類問題：在沒有資料時捏造一個臨床數值。應該一起處理。

## 三、對分批計畫的意見

順序要調整。第 0 批要先寫 mock、e2e、截圖流程，才去修會遺失資料的 bug，而資料每天都在寫。我建議先出一個小的熱修：`writeDay` 改成先 `update`，遇到 `invalid_argument` 就 `get()`，文件不存在才 `set({date,...patch})`；加上 N1 的載入閘門、B4，以及 N2 的 profile 寫入。用 mock 跑幾個 node 小測試就能驗證，之後再做工具。兩台裝置同時建立當天文件的競態還會殘留一個極小的空窗，除非用 `acquire`，否則消除不了。以一到兩台裝置的使用量，可以接受。

完成的定義：B1 的定義要寫明 latency compensation 開與關兩種都測。第 4 批的「截圖逐頁比對沒有舊卡片樣式」是主觀判斷，無法驗證，應改成可自動檢查的條件，例如子頁不再出現 `.card`、`.stat`。第 5 批的「逐像素差異只限字型抖動」很脆弱，改成「固定時鐘與資料下，各頁渲染後的 DOM 字串相同」比較可靠。

範圍：第 4 批改的是低頻使用的子頁，風險和工作量都最大，價值最小。我會只做 M1、M2、M6/N6、V3、V6，V1、V2 的全面改版延後。第 5 批的全檔重排建議縮小到「把日期函式放進有標記的區塊，讓測試抽得出來」。964 行的單檔整個重排，好處有限，卻會讓日後 `git blame` 和比對都變難。

## 四、Q1–Q4

**Q1** 同意 (a)：首頁顯示「—」，第一次用鍵盤輸入。這件事一生只發生一次，起始值未知時鍵盤最準；而目前的尺只涵蓋 ±10 kg。

**Q2** 允許不動尺就存，按鈕寫「和上次一樣 52.9 kg」。和上次同重是真實的量測結果，強迫撥一下尺只會養成無意義的動作。體脂則維持「沒動就不存」。

**Q3** 截圖不進 repo，需要時附在 PR 說明裡。二進位檔會讓 repo 一直變大，而且 CLAUDE.md 對截圖本來就劃了紅線，就算是合成資料，也容易被誤用成放真實截圖的先例。

**Q4** 第 1 項值得處理。正常的超音波目前會自動排 12 個月後再做，和頁面自己寫的「無常規追蹤建議」互相矛盾。根據 PubMed 檢索，USPSTF 建議不對無症狀成人做甲狀腺癌篩檢（Bibbins-Domingo et al., 2017, [DOI](https://doi.org/10.1001/jama.2017.4011)）。但家琳在服 levothyroxine，醫師可能另有安排。所以建議改成「不自動排程，有醫師指定才排」，最後由使用者決定。第 2 項優先度低，可以維持「依醫囑」。第 3 項同步 `docs/exam-intervals.md`，零風險，應該做。

## 五、總結

我不會照原樣開工：先把 N1（載入前寫入與錯誤劑量）和 N2 併進 B1，當作熱修放在第 0 批之前；mock 補上 latency compensation；B6 降為「手機實測後再決定」；第 4、5 批縮小範圍。
