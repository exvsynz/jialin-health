## F1｜高｜C2：重讀與補寫之間的新修改會被 verifyCreate 蓋回舊值

**位置：** `src/index.html:953`、`:957`–`:958`；`docs/specs/phase-C.md:190`–`:191`；處理說明第 54 行；`dev/merge-test.js:71`–`:76`（M8）。

`goneOf` 只能判斷讀取快照當時缺少哪些欄位。後面的 `update(g)` 沒有「欄位仍不存在才補」的條件，遞迴合併仍會覆寫同名葉節點。`queued(path)` 只串行本頁寫入，另一台更新既有文件不受它約束。因而「另一台的欄位會保留」「值不同的不動」只在讀到快照時成立，不能推到補寫提交時。

**已重現：** 抽取目前原始 `mergeDoc`／`verifyCreate`，用兩個隔離 VM context、共享的遞迴合併儲存層與受控提交時間：

1. A 在 t=0 取得租約並送出建立 `{am:{w:52}}` 的 set，暫停提交。
2. t=11 秒，B 取得新租約，建立同一天，內容包含 `med:{taken:true,at:"08:00",dose:50}`。
3. A 的遲到 set 提交，B 的 med 消失。
4. B 的 12 秒核對讀到 med 不存在；在快照取得後、補寫前，另一裝置合法寫入 `med:{taken:true,at:"09:00",dose:75,mode:"bedtime"}`。
5. 核對的 update 最後提交，得到 `med:{taken:true,at:"08:00",dose:50,mode:"bedtime"}`：時間與劑量被覆寫，還組成了混合紀錄。

這是 contract 允許的故障時序，不是正式 runtime 的事故紀錄。

**修改建議：** 不要把 `update` 描述成不會蓋掉他機修改。若要求這項保證，0.2.94 沒有條件式 update，不能靠再讀一次達成；應將衝突候選另存並提供恢復，或採取能避免同名資料競寫的模型。若保留使用者選定的乙方案，必須明列這個新增的自動補寫風險，不能只列關頁與遲到 set 晚於核對兩項限制；也不要把加租約或多讀一次當成完整保證。

**測試缺口：** M8 把他機修改放在核對開始前，測到的是 `goneOf` 能略過已存在的值；沒有在核對 get 與 update 之間插入他機更新。應加入上述時序，並斷言另一台新寫的時間、劑量或 `med:null` 不被補寫覆蓋。

## F2｜高｜C2：恢復只保存建立時的 body，可能復活已撤銷的紀錄

**位置：** `src/index.html:957`–`:958`、`:976`、`:1427`；`docs/specs/phase-C.md:188`–`:195`；處理說明第 47、54 行；`dev/merge-test.js:60`–`:69`（M7）。

核對保留的是第一次 set 的 `body`。建立後的成功更新、撤銷、刪除與估算結果不會更新這份恢復候選。遲到 set 可以抹掉它落地前的多筆修改，並非只會遺失另一台的第一筆紀錄。

**已重現：** 沿用 F1 的雙裝置時序，但沒有核對期間的第三筆競爭寫入：B 建立服藥後先成功撤銷，寫入 `med:null`（與頁面「撤銷」相同）；A 的遲到 set 再把整個 med 欄位抹掉；B 核對時，從原始 body 補回 `med:{taken:true,at:"08:00",dose:50}`。最後畫面會把已撤銷的服藥重新當成已記錄。即使兩頁都開著、遲到 set 在核對之前落地，仍然發生。

同理，若第一筆建立的是餐點，後來的完成結果或 `deleted:true` 被遲到 set 抹掉，原始 body 只足以補回建立時的餐點；不會恢復後續結果或刪除標記。若兩台建立的同名欄位都存在但值不同，`goneOf` 也無法還原雙方歷史。這些都超出處理說明「只要在核對之前落地，兩邊都會保留」的保證。

**修改建議：** 至少在本頁成功改動某欄位後，更新或淘汰相應的建立時恢復候選，避免補回自己已撤銷的值；要保留可恢復性，須保存後續已確認動作（包括 null／刪除標記／估算結果）。這只能解決過時候選，不能解決 F1 的跨裝置競爭。同步更正限制：只嘗試補回建立候選中缺失的欄位，並非恢復整份最新紀錄；核對讀寫失敗目前也會被靜默略過。

**測試缺口：** M7 用 `externalSet` 注入「已被整份覆蓋」的狀態，確實驗證最簡單的補回路徑，但沒有實際執行兩裝置取得租約與延遲提交，也沒有建立後的撤銷／第二筆更新。它不能證明上述保證。應保留 M7，另加可暫停 set 提交的雙裝置測試，以及建立→撤銷／完成／刪除→遲到 set→核對的案例。

## F3｜高｜C1：未能確認縮圖是否存在，仍會輸出標為 all 的漏圖備份

**位置：** `src/index.html:1886`–`:1892`；`docs/specs/phase-C.md:568`；`dev/review-c-test.js:29`–`:36`。

新增的 `mayThumb` 可以找到旗標寫入失敗的縮圖，但匯出把「get 成功且 exists:false」與「get 全部失敗，根本不知道是否存在」合併處理。只要 `promised` 為 false（例如 `thumb:false, thumbBytes:20000`），後者也不加入 missing。

**已在瀏覽器重現：** 使用 C1-2 同樣的持久狀態：餐點 `thumb:false, thumbBytes:20000`，對應縮圖文件確實存在。讓該縮圖的 get 四次都 reject `unavailable`。頁面完成退避後下載備份，結果為：

```text
實際縮圖存在：true
collections.mealthumbs：{}
thumbs：{"included":"all"}
畫面訊息：已匯出
```

使用者依賴這份完整備份搬移或清除原資料，仍可能永久失去照片。現有 C1-2 測試只涵蓋縮圖讀取成功，沒有驗證這個失敗分支。

**修改建議：** 分開處理確認不存在與讀取失敗。對任何 mayThumb 候選，重試耗盡仍未取得快照就必須標 partial／missing（或停止完整匯出），不能按旗標推定不存在；只有成功讀到 `exists:false` 才能套用「本來就可能沒有縮圖」的規則。同步修正規格 5.6，增加讀取失敗後完整性標記與檔名的測試。

## F4｜中｜C3：舊 pending 備份仍會回退已完成估算，缺少匯入正規化

**位置：** `src/index.html:899`–`:902`、`:1910`–`:1913`、`:1929`；`dev/review-c-test.js:39`–`:49`。

新的估算開始資料不寫 status，能避免新建 attempt 的問題；但舊資料與舊備份中的 `status:"pending"` 原封不動通過匯入。讀取端認得舊格式，不等於匯入端已向後相容。即使備份是在新版頁面匯出，只要資料庫保留舊 pending，仍會帶出該欄位。

**已在瀏覽器重現：** 目前相同 mealId／attemptId 已 `done`，範圍 400–600 kcal；匯入合法 v3 備份，該 attempt 帶 `status:"pending"`。匯入後 status 變成 pending，原數值仍在，但畫面顯示「1 餐沒有熱量」「估算很久沒有更新」，逐餐回退預覽未列出估算回退。這就是原 C3 的舊格式案例。

**修改建議：** 在匯入 payload 合併前，把舊 attempt 的 `status:"pending"` 正規化成省略 status；保留 startedAt 等開始資料，讓既有 done／failed 不被覆寫。此轉換不需讀取目標狀態，也能避免匯入期間結果落地的競爭。只移除備份 payload 的 pending 欄位，不能直接去清除資料庫中的終態。

**測試缺口：** 現有 C3 測試只由新版程式產生備份，未覆蓋原始舊格式。另外，它沒有斷言備份內的 attempt 在匯出時確實未完成；只靠 2500ms 與固定等待，在負載較高時可能匯出 done 後仍通過。應增加舊格式 fixture，並以可控制的 sample 完成閘門固定順序：備份確含開始資料且無終態→釋放模型結果→確認 done→匯入→結果仍可用。
