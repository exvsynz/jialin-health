主要風險在排程交付與舊資料處理，不在正常的開關合併路徑。 開關只寫單一 remind key，設定表單不寫 remind，本機寫入也有佇列；在正式 SDK 確實採遞迴合併的前提下，不同開關及「儲存設定」不會互蓋。不過 repo 只有 mock 宣稱此契約，沒有原始 db.d.ts，目前測試也不足以獨立證明正式環境的行為。

以下是需要修改或補證據的地方。

1. 高｜「（無需提醒）」不能保證不推播；有缺時也可能走兩條通知管道。
   位置：morning.md:82，evening.md:114–118、weekly.md:116–120。

   「不呼叫推播工具」只能控制工具呼叫，不能控制平台是否把最終回覆自動通知。反過來，同時呼叫推播工具並輸出同一句最終回覆，也可能重複通知。規格第 7 節已承認需要平台實測，因此這是尚未完成的上線驗收項目，不是已證實每次都會誤推。

   建議固定一種交付方式，並把無訊息分支寫成：「完成心跳後，以平台正式支援的不通知方式結束；不要輸出『無需提醒』或完成摘要。」但換句提示詞仍不是可靠保證；須取得平台明確的抑制通知機制並實測無缺、暫停、關閉、late 四種情境。我查到的 Anthropic 官方排程說明沒有提供可保證靜音的特殊回覆字串。

2. 中｜pushed:true 記錄的是意圖，不是推播結果。
   位置：morning.md:67、:78–85；其他兩份同樣；remind-ref.js:75。

   心跳先寫 pushed = !!msg，之後才送通知。通知工具失敗、工作階段中止，或平台未發出通知，都可能留下 pushed:true。反之，心跳寫入重試失敗後仍送通知，會有已推播卻沒有紀錄的情形。因此不能單靠 recent 驗收漏報或送達率。

   建議分開「應提醒」與「交付結果」，例如新增 shouldPush、deliveryStatus；只有工具確認成功才記已提交，平台代送則記未知。不要將「工具接受」再解釋成「手機收到」。

3. 中｜心跳讀取失敗沒有完整分支，從零開始的工作階段無法確定如何安全寫回。
   位置：morning.md:29、:36、78–80；weekly.md:32、39、112–114。

   第 2 步要求讀心跳，但錯誤判斷沒有包含它。若讀取失敗，就不知道文件是否存在、版本是多少，也不知道原本的 recent；後面的「存在／不存在」兩個寫入分支都無法正確選擇。正式服務若嚴格要求版本，可能拒絕寫入；不能假設它一定允許覆寫，也不能把錯誤當作空文件。

   建議明訂：心跳讀取失敗先有限次重試；仍失敗時不得以空 recent 或無版本 set 取代未知文件。週報也不得把無法取得的排程次數報成 0/14。另外補齊非版本衝突、重讀失敗及首次建立競爭的處理。

4. 中｜版本重試保住部分歷史，但沒有防重複通知，也不保證「最新」心跳真的是最新。
   位置：morning.md:70、:78–80；remind-ref.js:76。

   兩個工作階段讀到相同版本，第二個衝突後重讀 recent 再寫，這點方向正確。但仍有兩個缺口：

   - 同一排程被重跑時，兩個工作階段都會推播；週報的去重只處理計數。
   - 較早建立的 entry 若較晚完成，會放到陣列最前並取代頂層狀態；直接 slice(0,21) 並不等於保留時間最新的 21 筆。重複執行也會擠掉一週內的有效紀錄。

   建議加入穩定的執行識別碼，合併時去除同一次執行的重複項、依時間排序，再保留 21 筆；頂層取最新項。通知另需執行所有權或交付去重，單有 if_version 無法保證只送一次。

5. 中｜異常數字時間會讓心跳功能連帶打斷今天頁重繪。
   位置：index.html:514、:520、639。

   已重現：hbStatus({at:1e20}, now) 拋出 RangeError: Invalid time value。Number.isFinite(at) 不代表它是 JavaScript 可表示的日期。由於 renderToday() 直接呼叫 renderHb()，錯誤不只影響狀態行，也會中斷後續元件更新，違反舊心跳任意形狀不得影響其他功能的要求。

   建議在格式化前檢查 new Date(ms).getTime() 是否有效；ISO 字串也應要求明確的 Z／時區偏移，避免無時區字串依裝置時區解讀。補超範圍數字與無時區字串測試。

6. 中｜週報對舊 recent 的防護發生得太晚，參考實作與提示詞也不完全一致。
   位置：remind-ref.js:48、:76–77；weekly.md:48、:106–108。

   已重現：週報遇到 recent:{} 或 recent:[null] 會拋錯。雖然組新心跳時有 Array.isArray，週報在那之前就已遍歷它。提示詞也把「非陣列視為空」放在計算週報之後。另外，參考實作直接複製舊項目，會保留舊項目內嵌的 recent，不符合提示詞「每一筆都不含 recent」。

   建議讀取後立即共用正規化：確認陣列、過濾無效項、驗證時間與 kind/date，並只保留允許欄位；計數與寫回都使用同一結果。

7. 中｜快速切換開關時，舊請求會清掉新請求的暫存狀態。
   位置：index.html:1033。

   已用抽出的事件處理器重現：先關、隨即開，第一筆完成就執行 delete remindPending[k]，此時第二筆仍在等待。接著畫面可能回到第一筆的值，並顯示已過時的「已關閉」toast。資料庫佇列本身仍照順序寫，但使用者會看到開關反跳，可能再點一次造成非預期設定。

   建議每個 key 加操作序號，只有最新請求能清除 pending、重繪結果及顯示撤銷 toast。測試應加入慢網路下的連續切換、第一筆失敗及撤銷。

8. 中｜舊紀錄的到期日會在頁面存在，卻被提醒靜默略過。
   位置：remind-ref.js:30、evening.md:79；對照 index.html:936、規格 §2.4。

   已重現：thy_lab 紀錄日期為 2026-07-01、interval:null、無 nextDue，設定間隔為 3 個月時，頁面算出 2026-10-01，參考實作卻回傳 null。規格雖有寫明此差異，但「目前表單不會產生」不能涵蓋舊資料或匯入資料，也不足以符合 CLAUDE.md 的向後相容要求。

   建議補齊相同 fallback，包括 settings/intervals 與 noFollow；或先完成有驗證的資料遷移。不要在排程中另猜臨床預設值。

9. 中｜late 只看當下時段，不能識別跨日延遲；長時間執行也沒有最後檢查。
   位置：morning.md:19、:39；evening.md:19–21、40；remind-ref.js:24。

   一般的台北時區與 04:00 換日邏輯正確。但若昨天早上的工作延至今天早上才開始，它仍會被視為正常；週報延一週也一樣。另一個邊界是晚上 03:59 開始，工具操作拖到 04:00 之後，仍可能依開始時的時間推播。

   建議使用排程提供的預定執行時間／執行識別碼判斷所屬批次，並在交付前再次檢查截止時間。若平台不提供這些資料，需明確承認只能限制「當下時段」，不能偵測完整一天或一週的延遲。交付前若重讀資料，也應同步重算邏輯日與缺漏，避免沿用舊日訊息。

10. 中｜關閉或暫停提醒後，讀取錯誤仍可能每天推播。這是規格層的使用負擔。
    位置：evening.md:37、weekly.md:39–42；規格 §3.1。

    例如已讀到 remind.evening:false，但 records 讀取失敗，第一條仍優先產生錯誤推播。暫停及 late 也相同。這符合目前規格順序，但「關閉」不等於使用者直覺上的停止通知。

    建議在已知關閉／暫停／超時時停止不必要的資料讀取，將錯誤留在心跳狀態；若要讓故障通知突破關閉，至少須明確定義其語意。這不涉及第 8 節已確認的決定。

11. 中｜「需盡快處理」含有臨床急迫性判斷，不能只視為日期格式化。
    位置：evening.md:80、weekly.md:82；既有來源為 index.html:915。

    這不是 A 階段新增間隔，但把所有 interval:0 都推成「需盡快處理」，會把原頁面較完整的處置條件壓成急迫性文字。例如既有 Lung-RADS 0 預設為 0，說明是「依報告指定時間補做」。

    ACR Lung-RADS v2022 原始文件的 Category 0／註 9–10 包括等待舊影像比較，以及感染或發炎情境的 "1–3 month follow-up LDCT"，並非一律相同急迫性。建議保留既有間隔，推播改忠實表達「待依報告處理」，或使用明確儲存的處置文字；不要由排程自行推導急迫程度。週報的體重平均本身沒有新增升降評價。

12. 低｜今天頁對無法解析時間也顯示警示，與第 8.5 節的條件不完全一致。
