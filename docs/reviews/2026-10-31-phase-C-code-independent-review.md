## C1｜高：完整備份可能漏掉已存在的縮圖，仍標記為 all

**位置：** `src/index.html:1155`、`:1157`（縮圖及旗標分開寫入）、`:1315`（清除清單）、`:1867`（匯出選圖）、`:1910`（匯入合併）。對應規格 5.6、D5／D7，以及 R3／R4。

**問題：** 匯出與清除工具只相信 `thumb === true && !thumbCleared`，沒有核對對應縮圖文件。兩條正常操作／失敗路徑會使旗標和實際照片不一致：

1. 清除舊縮圖寫入 `thumbCleared:true`，再匯入清除前的完整備份。備份沒有 `thumbCleared`，遞迴合併會保留現在的 `true`，但 `mealthumbs/{id}` 已被還原。下次完整匯出跳過這張照片，清除工具也看不到它。
2. `mealthumbs/{id}.set` 成功，後面的 `writeDay(...thumb:true)` 失敗，未完成「再存一次」就關頁。照片仍在資料庫，但新頁面的 `thumb:false` 使它永遠不進匯出清單。

**重現與結果：** 第一條已在 Chromium 實際匯入、匯出；得到 `thumbExists:true`、`exportedThumbs:{}`、`thumbs:{included:"all"}`、`thumbList:[]`。第二條用原始 `exportAll` 在 VM 重現上述持久狀態，照片存在但縮圖讀取次數為 0，匯出同樣標記 `all`。使用者依賴這份「完整備份」搬到新資料庫或清除原資料後，會失去照片。不是只有顯示問題。

**修改建議：** 成功匯入縮圖後，協調更新對應餐點的 `thumb:true`／`thumbCleared:false`，更新失敗須算未完成、可重試。完整匯出應對餐點 ID 逐筆核對縮圖，或採用可恢復且能驗證的縮圖索引；不要查詢整個含 data URI 的集合。沒有確認的項目不能標為 `all`。清除工具也須能修復旗標不一致。加入「清除→還原→再匯出」及「圖存成功、旗標失敗→重開→匯出」測試。這也需要補強規格本身的選圖規則。

## C2｜高：發送前的 7 秒檢查無法阻止過期租約下的 set 覆寫 A／B 資料

**位置：** `src/index.html:945`、`:959`–`:962`；`docs/contract/0.2.94/db.d.ts:420` 起。對應 R2。

**問題：** 程式只在送出 `set(body)` 前檢查時間。請求送出後若延遲超過 10 秒租約，另一裝置已能取得租約並建立同一天；第一個遲到的整份 `set` 仍會覆寫它。contract 說的是 cooperative lease；寫入沒有附租約 token，也沒有條件式 create／CAS，因此不能假設伺服器會拒絕過期持有者的寫入。

**重現：** 用原始 `mergeDoc`、兩個隔離的裝置 context 與可控制提交時間的儲存層：

1. A 在 t=0 取得租約，讀到文件不存在，送出 `{date, am:{w:52}}`，暫停它的 set 提交。
2. t=11000，B 取得新租約，讀到仍不存在，成功寫入 `{date, med:{taken:true}}`。
3. 讓 A 的 set 提交。最終只剩 `date` 與 `am`，B 的 `med` 消失。

這是依 contract 所允許時序的確定性故障注入，**不是宣稱已在正式 Artifact 觀察到伺服器故障**。

**修改建議：** 修正程式註解及驗收敘述，不能宣稱兩台裝置絕不會同時建立。可續租並在逾時後停止發出新 set 以降低風險，但這無法撤銷已送出的寫入；若要保證不覆寫，須避免多裝置以整份 set 建立同一個共享日文件，例如評估獨立且唯一 ID 的寫入資料模型，或受控的單一建立者流程。不要把另一個 get-then-set 當成原子解法。沒有租約能力時的 fallback 亦需明載同樣限制。

**與 main 的關係：** 這是既有風險未完全消除，並非本次才引入。C 把 3 秒改成 10 秒、拒絕把一般 acquire 錯誤當成功、set unavailable 後重新取得租約，都是改善。現有文件的遞迴 update 路徑未發現 A／B 欄位回歸；風險集中在缺文件時的建立。

## C3｜中：舊 pending 備份會讓已完成的同一次估算退回 pending，預覽未列回退

**位置：** `src/index.html:1889`、`:1910`、`:889`。對應 R4、規格 5.6。

**重現：** 拍照後估算尚 pending 時匯出；等同一 attempt 完成（合成結果 400–600 kcal），再匯入剛才的備份。相同 `attempts[a].status` 被改成 `pending`。數值欄位仍在，但 `isDone` 不承認它，`mealView.kcal` 變成 `null`。匯入預覽的逐餐回退計數只看 manual／note／meal／at／deleted／ref，不包含 attempts，因此不會指出這次估算回退。已在瀏覽器重現。

**影響：** 完成的估算從正常使用畫面消失，使用者可能再次估算及消耗次數。此項不是數值已被物理刪除，但仍破壞恢復後的可用狀態。

**修改建議：** 對同一 attempt 採不可倒退的完成語意，避免 pending metadata 覆蓋終態；可考慮將開始資料和完成結果放在不同且不互相覆寫的欄位。需同時考慮匯入期間結果落地，不能只在匯入前讀一次狀態、再無條件寫回。若仍允許回退，至少在預覽明列影響與恢復方式。新增「pending 備份→done→匯入」測試。

**規格界線：** v2 確實允許備份中相同欄位後寫覆蓋；本項是該設計與「估算結果會保留」目標的缺口，不能全部歸為沒有照規格實作。

## C4｜中：重新估算沒開始成功，補充說明仍被當成已存，之後儲存會丟失文字

**位置：** `src/index.html:1288`、`:1230`–`:1234`、`:1298`–`:1302`。

**重現：** 開啟一餐，讓原圖不在本頁記憶體且資料庫沒有縮圖；輸入 `half bowl` → 按「重新估算」（提示沒有照片）→ 按「儲存」。畫面正常關閉，但資料庫 `note` 仍為空。已在瀏覽器重現。

**修改建議：** 只在 note 確實寫入成功後才更新表單基準；讓 `reEstimate` 回傳是否成功保存，並核對仍是原本開啟的餐點。失敗時保留 dirty 狀態。缺圖與 pending 寫入失敗都應加入回歸測試。

## C5｜中：跨過六分鐘時，等待提示不會自動變成可重試

**位置：** `src/index.html:1207`、`:1923`；規格的中斷／另一裝置估算恢復流程。

**重現：** 開飲食頁，餐點的 pending 已五分鐘，且本頁沒有對應 inflight。用瀏覽器時鐘推進兩分鐘、沒有新 snapshot。仍顯示「估算中…」，沒有重新估算入口；手動觸發 `renderCur()` 才顯示「估算很久沒有更新」。已在瀏覽器重現。

**修改建議：** 定時更新餐點狀態、今天飲食列及開啟中的單餐狀態，保留正在編輯的輸入及焦點。只刷新狀態；不要把六分鐘誤做 sample 自訂 timeout，也不要自動再次呼叫模型。

## C6｜中：sample mock 在等待同意時取消，下一次呼叫會跳過尚未完成的同意決定

**位置：** `dev/mock-claude.js:150`–`:152`；`docs/contract/0.2.94/sample.d.ts:304`–`:307`。

**重現：** mock 設 `consent.wait=1000`；第一個 sample 等待約 30ms 後 abort，再發第二個不同輸入。實測第一個回 `cancelled`，第二個幾乎立即完成並計一次 upstream（合計約 31ms），沒有等到一秒的同意決定。

**原因：** `consentAsked=true` 在 await 前寫入。abort 讓 await 退出，但 `consented` 仍為 null；下一次看到 consentAsked 已 true 就繼續。contract 明定取消這次呼叫時，同意視窗仍開著，其答案支配後續呼叫。

**修改建議：** 用獨立於單次 signal 的共用 consent promise 表示同意視窗生命週期。各次呼叫可以停止等待，但不能把未回答視為已允許。加入第一個取消、第二個仍等待，以及最終拒絕後第二個也不能 upstream 的測試。這是測試替身的保真問題，不是正式頁面繞過平台授權。
