## 結論

建議先補齊四項高風險問題，再開始 C 階段實作：同餐估算與手動修改的跨裝置競爭、既有建立租約失敗後的覆蓋風險、儲存失敗恢復流程，以及匯入與進行中寫入的協調。

## 審查發現

### R1｜高：同餐手動修改與重新估算缺少跨裝置競爭處理

**位置：**規格 §4.4 L273、§3.4 L174–177、§5.4 L374；`src/index.html` L760–784。

**問題：**A 裝置根據本地資料判斷尚未 `edited`，B 隨即儲存手動熱量，A 再寫入估算，仍可能覆蓋 B。另一個情境是 B 的新估算已完成，A 的舊成功、舊失敗或取消回覆才到，將新的結果與狀態蓋回舊版本。六分鐘「中斷」只改顯示，不會終止另一台的請求。

`writeDay` 的 queue 只在同一頁面內生效；遞迴合併不同餐點 id 也不能解決同一餐同一欄位的競爭。

**修改建議：**

- 自動估算只寫估算資料，手動覆寫另存，由顯示層選擇目前採用值，避免回覆寫入手動欄位。
- 每次估算有唯一 `attemptId`，定義目前採用哪次嘗試，以及舊結果如何被排除。
- 不要只加本頁快照檢查或「先讀再寫」；這仍有檢查後被另一台改動的空窗。
- `db.d.ts` L393–415 明定 last-writer-wins、沒有 transactions，`DocumentReference` 沒有暴露 CAS／條件版本寫入；不可用不存在的 API 解決問題。`acquire` 雖回傳 version，也不代表可用該值條件寫入。
- 若用租約協調，須遵守 `db.d.ts` L420–436 的合作式語意；直接 `update/set` 不會被租約攔住。可優先設計獨立手動覆寫、依 attempt 儲存結果及選擇目前結果，避免把短租約持有整段模型呼叫。

**驗收：**手動值與回覆交錯、兩台重估反向完成、舊請求取消／失敗晚到、新 note 不被舊結果代表。

### R2｜高：D1 對既有建立租約的保證過強，且覆蓋可重現

**位置：**規格 §2.1 L98、D1 L699；`src/index.html` L768–778，尤其 L773–774。

**問題：**`acquire()` 出錯被吞掉，程式繼續沿用預設的 `acquired: true`，退化成無保護的 `get → set`。

**實際重現：**使用現有 `mergeDoc` 原函式，讓兩台裝置的初次 `update` 都回報文件不存在，`acquire` 都拋出 `unavailable`，兩次 `get` 都讀到不存在，再各自 `set` 不同 meal id。最後文件只留下後一台的餐點。

**修改建議：**取得租約失敗時不可當作成功；保留待存內容並顯示可重試。`db.d.ts` L420–436 已確認租約是合作式、沒有 release、須在有效期間內完成臨界區或續租，且所有相關呼叫端都必須配合。現有固定三秒租約不能在網路延遲下無條件保證安全。這是既有 helper 的缺陷，C 規格應列為實作前置修復，而不是假設已解決。

**驗收：**取得租約失敗、租約有效期間不足、兩台同時建立當日文件；不能只測兩台對既有文件合併不同 meal id。

### R3｜高：初始儲存、縮圖儲存與結果回寫沒有完整恢復流程

**位置：**規格 §5.2 L319–337、§4.4 L255–274。

**問題：**規格同時啟動寫入與估算，卻未定義何時能宣告「已存」。初始餐點儲存失敗後，結果 patch 可能自行建立只有 `est` 的殘缺餐點；縮圖成功、餐點失敗則留下孤兒縮圖。模型成功但結果寫回失敗，也沒有清楚的重存方式。未存餐點「離開頁面就消失」，而重存入口只在飲食頁，與拍完留在今天頁的正常使用方式衝突。

**修改建議：**

- 明定基礎餐點、縮圖及估算結果各自的狀態與成功條件，只有確認成功才能說已存。
- 基礎餐點未成功時，不允許結果 patch 自行建立餐點。
- 待存內容至少保留整個開啟工作階段；切換今天／飲食頁不得丟棄，今天頁也要有持續可見的重存入口。
- 重新存入已取得的模型結果不應再次消耗模型呼叫。
- 定義縮圖成功、主紀錄失敗的重試與孤兒處理，以及關閉整個 Artifact 後仍可能失去的內容。
- 若要新增持久化草稿，須另行明定健康資料存放位置與保留政策，不能暗中把原圖寫進持久儲存。

**證據邊界：**同頁 `writeDay` 有 queue，不能直接宣稱快速模型回覆必然先於已排入 queue 的初始 pending 寫入；本項針對失敗流程與未明定的順序。

### R4｜高：整份匯入與進行中的估算／另一台寫入互相破壞

**位置：**規格 §5.6 L415–416；`src/index.html` L1450–1469。

**問題：**目前匯入直接 `set(data)`，不經 `writeDay` queue。舊備份可抹去剛新增的餐點；晚到的估算又可能在匯入後加回不完整餐點。新增 `importLoses` 規則只檢查缺少 meal id，沒有涵蓋同 id 的手動值、備註、估算與刪除狀態回退。

**修改建議：**定義匯入期間的寫入協調、既有估算失效規則與跨裝置衝突處理；只停用本頁按鈕不夠。若無法安全實現整日覆蓋，考慮飲食資料逐餐合併並明示同 id 衝突。預覽須涵蓋同 id 資料取代與已刪餐點復原。

**驗收：**匯入與模型回覆交錯、匯入與另一台加餐交錯、同 id 手動值回退、刪除後匯入舊備份。

### R5｜中：部分備份與無縮圖備份缺少完整性及還原規則

**位置：**規格 §5.6 L405–416、D5 L713–715。

**問題：**有些縮圖讀不到或刻意不匯出時，`days` 仍可能保留 `thumb: true`。在空資料庫還原後，引用的圖片不存在，卻可能仍提供重估。只有當次 toast 無法讓日後拿到備份的人知道缺了哪些資料。

**修改建議：**備份記錄完整性、缺圖 id 清單及「刻意不含縮圖」狀態。匯入後核對目標資料庫實際存在的縮圖，再處理旗標與重估能力；不能一律假設備份未附圖代表目標也沒有圖。部分備份要清楚命名與標示，不當作完整備份。

**驗收：**缺圖備份還原到空庫／有既存縮圖的庫、部分下載、匯入縮圖寫入失敗、引用一致性。

### R6｜中：容量滿時，先匯出並不能恢復儲存能力

**位置：**規格 §2.2 L108–113、§5.2 L329–332、D4 L710–712。

**問題：**匯出不會釋放 DB 空間；軟刪餐點永久保留縮圖，沒有清理途徑。容量滿時文字餐點也不保證能存。「約十五年」只是文件數的粗估，未涵蓋既有集合及孤兒文件，更不是總容量保證。

**修改建議：**區分「縮圖未存、文字已存」及「整餐未存」。定義備份後可選的縮圖封存／清理方式，說明撤銷及重新估算受到的影響；不可自動刪除照片。容量估算標明假設，實際上限未查得就保留未知。縮至 240 px 仍超過 32 KiB 時，也要有明確後續分支。

**型別證據：**`db.d.ts` L200–208 明定文件數滿額與總大小滿額不同：後者也可能拒絕讓既有 `days` 變大的寫入。L547–553 確認每文件 256 KiB、全庫 25,000 文件；總容量數值仍未提供。

**驗收：**圖片額度不足、所有寫入均失敗、清理後引用一致性；壓縮測試應包含合成的高細節影像，不能只用容易壓縮的色塊。

### R7｜中：凌晨補登及時間編輯存在日期偏移

**位置：**規格 §3.1 L145、§5.4 L373、§5.5 L391。

**問題：**台北 11/1 02:00 時，`viewDate` 已是 10/31；相簿 fallback 再組成「10/31＋02:00」，邏輯日就落到 10/30。只改時間但不允許改日期，也未定義如何保持餐點所在文件與 `at` 一致。

**修改建議：**使用統一的「邏輯日期＋鐘面時間」轉換：凌晨四點前對應下一個日曆日，維持 `logicalDate(at) === days 文件日期`。日期更正不宜要求刪掉重加，因原圖可能已不存在；若新增移動功能，需明定跨文件失敗恢復與縮圖引用。

**驗收：**凌晨相簿 fallback、03:59／04:00 時間編輯、非台北瀏覽器時區、日期更正中斷。

### R8｜低：能力缺席的原因說明不準確；手動記餐可用性屬產品選擇

**位置：**規格 §4.1 L192–198、§5.1 L299–301。

**問題：**§5.1 說只有沒宣告 `sample` 才會隱藏，並不正確；`use()` 也可能因該 view 不提供能力、初始化未授權或模組載入失敗而回傳 null。`limits()` 拒絕或缺少 images 同樣要隱藏相關能力。

**本次修正：**`sample.d.ts` L192–205 明確要求將 limits 拒絕視同 images 缺席；L674–687 要求永久缺席／拒絕時隱藏相依功能。因此原規格的隱藏策略符合 contract，撤回將其當作契約問題或要求同 view 重查永久拒絕的建議。若希望保留記餐，可另外保留不呼叫 sample 的文字／手動輸入；不得藉此重新呼叫遭拒的能力。另修正「只有沒宣告」的原因說明，不向使用者猜測授權原因。

**點擊數判斷：**已同意的同一 view 內，頁面一次＋相機最多兩次符合三次限制。但同意不是只發生在首次使用此功能；每個新 view 的首次呼叫都可能詢問，需依 R16 明確列為例外或調整驗收。

### R9｜中：重新估算失敗時，當日合計是否保留有效值互相矛盾

**位置：**規格 §3.3 L168–169、§8.2 L567–568、§4.4。

**問題：**一處規定有效熱量即相加，另一處把 pending／failed 都列為沒有熱量；錯誤處理又要求保留手動值。不同實作可能讓按下重估後當日總數突然減少。

**修改建議：**合計依目前採用數值是否有效決定；估算狀態另行顯示。手動值或保留的上次成功值，不因新一次估算失敗而消失。統一 helper 定義、UI 與驗收文字。

### R10｜中：研究到產品設計的推論超出目前證據

**位置：**規格 §4.1 L207–210、§4.3 L248–250、§7.2。

**問題：**即使引用研究內容無誤，Sonnet／Opus 的比較也不能直接證明 runtime `modelTier: "default"` 對應同一模型或同樣準確度。十餐七餐覆蓋不能證明區間已校準為「七成機率」；無限放寬區間就能增加覆蓋率。單組十餐也不能檢驗加入台灣背景提示是否改善估算。

**修改建議：**

- 將十餐定位為初步個人試用，不宣稱統計校準或通用準確度。
- 同時記錄範圍寬度、估算失敗、原估算圖／縮圖、有無補充，避免只挑成功餐點。
- 比較提示詞需同餐配對；調整提示詞的資料不能同時當作獨立驗收。
- `default` 可作操作選擇，但不得把模型研究寫成它的直接驗證。
- 秤重換算值宜稱「參考值」，交代換算來源；僅有重量本身並不直接給出精確熱量。

### R11｜低：19 種總數正確，但「全部列在 §4.4」不正確

**位置：**規格 §4.4、§7.3 L506。

**已核實：**`sample.d.ts` L714–733 確實定義 19 種。規格表格 17 種加另述 `invalid_json` 為 18，缺少的是 `tools_unavailable`；`invalid` 仍是頁面本地碼。原報告將總數或漏項列為待查，本次確認總數無誤。

**修改建議：**保留 19 的總數，明列 C 不傳 tools，故 `tools_unavailable` 不屬正常可達路徑；若保留「完整枚舉」承諾，列出它並註記不適用。不需要為此增加沒有用途的 UI 或 tools 模擬。真正影響錯誤處理與 mock 的差異見 R12。

### R12｜中：錯誤處理原樣重試與 mock 的圖片超量錯誤碼不符 contract

**位置：**規格 §4.4 L268–270、§8.1 L534–540；`sample.d.ts` L653–672、L697–709。

**已核實問題：**

- `empty_completion` 與 `upstream_error` 被放在同一個「再估一次」分支，但型別 L703–705 明定 empty completion 不應原樣重送，應簡化要求或減少輸出；cache:false 只換新呼叫，並不修正輸入。
- invalid_request、transform_error、prompt_too_large、queue_overflow 是要修正呼叫的問題，不宜提供會原樣重做的通用按鈕。
- 規格 mock 將超過 maxCount 列為 invalid_request；型別 L697–698 明定圖片張數超量為 image_rejected。圖片參數不是合法 Blob 等，才屬 invalid_request。

**修改建議：**分開人工重試暫時錯誤、要求改輸入及程式錯誤三種處置；empty completion 可由使用者明確觸發較簡短的提示詞，或保留手動輸入，但不自動重試。不做隱藏的自動修復呼叫。修正 mock 並測試超張數、非 Blob、格式／大小問題各自的正確 code。

### R13｜中：六分鐘無回寫不能證明另一台估算已中斷

**位置：**規格 §3.4 L172–177；`sample.d.ts` L45–48、L70–81、L293–316。

**已核實問題：**約五分鐘是每輪模型處理上限，不是包含等待同意與排隊的端到端上限。另一台可能還停在同意視窗或等候執行，六分鐘後仍是有效請求。規格「估算沒有完成」若被解讀為舊請求已終止，再估一次就會造成兩個有效請求競爭。

**修改建議：**超時偵測僅作「較久未更新，可能仍在另一裝置等待」的顯示訊號，不宣告舊請求死亡、不寫 failed，也不加違反 contract 的取消計時器。重新估算仍須 R1 的 attempt 隔離，並明確處理舊請求晚到。補模擬長時間同意及排隊情境。

### R14｜低：快取作用域與命中保證需補充

**位置：**規格 §4.2 L220–224、§8.1 L543–548、§8.3 L613–617；`sample.d.ts` L421–456。

**已核實：**預設五分鐘、列出的鍵、成功但本頁解析失敗仍可被 sample 快取、cache:false 不讀／不存／不共享，以及同時相同呼叫共享回覆均有依據。但作用域還包含「同一瀏覽器」，快取是 best-effort，登出會清除；不能承諾跨裝置省用量，也不能把五分鐘內一定只呼叫一次上游當成正式 runtime 保證。

**修改建議：**補齊作用域與 best-effort 限制。mock 可用可控且確定性的快取測試，但須區分 mock 行為與實機保證；應用也要在未命中時正確工作。`gcTime` 的有效窗同時取決於儲存與讀取兩次呼叫的設定。

### R15｜低：採用 truncated 結果時缺少可見標記

**位置：**規格 §3.2 L162、§2.1 est 欄位；`sample.d.ts` L568–572。

**問題：**規格允許 truncated:true 但 JSON 合規時照常採用，卻未保存 truncated 或標示。sample() 的確可以成功回傳並快取截斷結果，故不能把它當成 sample.json() 的 invalid_json；但型別要求呈現時帶提示。

**修改建議：**若接受合規結果，保存截斷旗標並提供簡短的未完整提示；或產品決定將其判為本地 invalid，交由使用者修正輸入後重試。不可默默宣稱它是完整估算。

### R16｜中：同意視窗的「第一次使用」應改為每個 view 的首次呼叫

**位置：**規格 §1 L20–24、§4.1 L194、§11 L733；`sample.d.ts` L45–48、L434–435。

**已核實問題：**contract 明定每個 view 的首次呼叫仍會詢問，不是使用者只需在初次使用功能時同意一次。iOS 的頁面點擊、快門、使用照片再加同意，可能需要四次操作；重新開啟後仍可能發生。

**修改建議：**寫清楚三次點擊適用於同一 view 已同意後的記餐流程，另列每個新 view 的 consent 例外，並實測 ≤10 秒的計時範圍。不要為了避開相機後的同意而在載入時偷偷呼叫模型；規格採只在使用者動作後呼叫本身符合 contract。
